=== FILOSOFÍA TDD REAL — LEE ESTO ANTES DE GENERAR ===

En TDD real el ciclo es:
  🔴 RED:    La prueba importa el sistema real del proyecto. FALLA porque no existe.
  🟢 GREEN:  El desarrollador implementa el sistema real. La prueba PASA.
  🔵 REFACTOR: El desarrollador limpia el código. La prueba sigue pasando.

Una prueba de sistema valida el comportamiento completo desde la perspectiva del usuario:
flujos end-to-end reales, estado del sistema antes y después, reglas de negocio complejas.

Si el sistema se define inline dentro del test, la prueba se está probando a sí misma
y siempre pasará. Eso no es TDD de sistema.

Por lo tanto:

  ✅ codigo_pytest → importa el sistema/fachada REAL desde el proyecto.
                     FALLARÁ en rojo porque ese módulo aún no existe.

  ✅ codigo_implementacion → el contrato mínimo del sistema que el desarrollador
                              debe crear en su proyecto para que la prueba pase.

=== QUÉ ES EL PUNTO DE ENTRADA DEL SISTEMA ===

Para pruebas de sistema se importa una clase de "fachada" o "aplicación" que encapsula
todas las capas del sistema. Esta clase expone los casos de uso como métodos públicos
y maneja internamente el estado.

El desarrollador decide cómo implementar esas capas internas — la prueba solo verifica
el comportamiento observable desde afuera (inputs, outputs, estado).

=== CÓMO INFERIR EL MÓDULO DE IMPORTACIÓN ===

Infiere una fachada de aplicación realista a partir del nombre del proyecto.

Ejemplos:
  Proyecto "Sistema de Citas Médicas"   → from citas.aplicacion import AplicacionCitas
  Proyecto "Gestión de Inventario"      → from inventario.aplicacion import AplicacionInventario
  Proyecto "E-commerce"                 → from tienda.aplicacion import AplicacionTienda

La clase de aplicación recibe en su constructor los repositorios o dependencias externas
que el desarrollador implementará. En la prueba, esas dependencias se mockean.
