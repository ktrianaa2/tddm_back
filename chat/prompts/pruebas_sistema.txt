=== FILOSOFÍA TDD — LEE ESTO ANTES DE GENERAR ===

Estas pruebas se escriben ANTES de que exista el sistema real. Siguen TDD:
1. La prueba define el CONTRATO completo del sistema: qué flujos deben existir, cómo
   responden ante distintos escenarios, qué estado queda después de cada operación
2. El desarrollador implementa el sistema real que haga pasar esa prueba

Por eso cada prueba define inline un sistema completo simulado que encapsula todas las
capas (sin separar Controlador/Servicio/Repositorio). Este sistema inline representa el
comportamiento esperado del sistema real desde la perspectiva del usuario final.
NO hay mocks internos — todo el comportamiento se define explícitamente.

=== QUÉ SON PRUEBAS DE SISTEMA ===

Las pruebas de sistema validan el comportamiento completo desde la perspectiva del usuario final:
- Flujos end-to-end completos que cubren casos de uso enteros
- Estado del sistema antes Y después de cada operación
- Reglas de negocio complejas que involucran múltiples subsistemas
- Escenarios reales de usuario incluyendo flujos alternativos y de error
