=== FILOSOFÍA TDD REAL — LEE ESTO ANTES DE GENERAR ===

En TDD real el ciclo es:
  🔴 RED:    El desarrollador escribe la prueba. La ejecuta. FALLA porque el código no existe.
  🟢 GREEN:  El desarrollador escribe el código mínimo en su proyecto. La prueba PASA.
  🔵 REFACTOR: El desarrollador limpia el código. La prueba sigue pasando.

Para que este ciclo funcione, la prueba DEBE importar el código real del proyecto del
desarrollador. Si la prueba define la lógica inline dentro del test, nunca falla en fase
roja — se está probando a sí misma. Eso no es TDD.

Por lo tanto:

  ✅ codigo_pytest  → importa desde el módulo real del proyecto. Sin lógica inline.
                      FALLARÁ en rojo porque ese módulo aún no existe.

  ✅ codigo_implementacion → el contrato mínimo que el desarrollador debe crear en su
                              proyecto para que la prueba pase. Es una GUÍA, no va
                              dentro del test.

=== CÓMO INFERIR EL MÓDULO DE IMPORTACIÓN ===

A partir del nombre del proyecto y las especificaciones, infiere rutas de módulo realistas.
Usa snake_case y estructura de paquete estándar de Python/Django.

Ejemplos:
  Proyecto "Sistema de Citas Médicas"   → from citas.servicios import CitasServicio
  Proyecto "Gestión de Inventario"      → from inventario.servicios import InventarioServicio
  Proyecto "E-commerce"                 → from pedidos.servicios import PedidosServicio

Si el proyecto tiene nombre en español, usa ese nombre en snake_case como nombre del paquete.
La clase a importar debe seguir PascalCase y terminar en Servicio, Repositorio, o Controlador
según la capa que se está probando.

=== REGLAS PARA GENERAR PRUEBAS ===

1. COBERTURA OBLIGATORIA POR FUNCIONALIDAD:
   - Caso exitoso con datos válidos
   - Validación de campos obligatorios
   - Validación de formatos inválidos
   - Reglas de negocio específicas del dominio
   - Valores límite
   - Condiciones previas no cumplidas

2. CÓDIGO PYTEST — REGLA MÁS IMPORTANTE:

   El campo codigo_pytest SOLO contiene la prueba pura.
   IMPORTA la clase desde el módulo real del proyecto.
   MOCKEA únicamente las dependencias externas (repositorio, BD, APIs).
   NO define lógica inline — eso va en codigo_implementacion.

   ✅ CORRECTO:
   "codigo_pytest": "def test_crear_cita_paciente_inexistente_lanza_error():\n    from unittest.mock import Mock\n    import pytest\n    from citas.servicios import CitasServicio\n\n    # Arrange\n    repo_mock = Mock()\n    repo_mock.buscar_paciente.return_value = None\n    servicio = CitasServicio(repo_mock)\n\n    # Act & Assert\n    with pytest.raises(ValueError) as excinfo:\n        servicio.crear_cita({'paciente_id': 999, 'fecha': '2024-01-15'})\n    assert 'paciente no encontrado' in str(excinfo.value).lower()\n    repo_mock.guardar.assert_not_called()"

   ❌ INCORRECTO — define la clase inline (la prueba se prueba a sí misma):
   "codigo_pytest": "def test_crear_cita():\n    class CitasServicio:\n        def crear_cita(self, datos):\n            raise ValueError('paciente no encontrado')\n    servicio = CitasServicio()\n    with pytest.raises(ValueError):\n        servicio.crear_cita({'paciente_id': 999})"

   ❌ INCORRECTO — mock trivial que siempre pasa:
   "codigo_pytest": "def test_crear_cita():\n    mock = Mock()\n    mock.crear_cita.return_value = True\n    assert mock.crear_cita({}) == True"

3. CAMPO codigo_implementacion — CONTRATO PARA EL DESARROLLADOR:

   Este campo contiene la clase/función mínima que el desarrollador debe crear en su
   proyecto para que la prueba pase. Es una guía de implementación, NO va dentro del test.

   ✅ CORRECTO:
   "codigo_implementacion": "# Archivo: citas/servicios.py\n\nclass CitasServicio:\n    def __init__(self, repo):\n        self.repo = repo\n\n    def crear_cita(self, datos):\n        paciente = self.repo.buscar_paciente(datos['paciente_id'])\n        if paciente is None:\n            raise ValueError('Paciente no encontrado')\n        return self.repo.guardar(datos)"

4. NOMENCLATURA:
   Formato: test_[accion]_[condicion]_[resultado]
   Ejemplos:
   - test_crear_cita_paciente_inexistente_lanza_error
   - test_crear_cita_fecha_invalida_lanza_error
   - test_crear_cita_datos_validos_retorna_cita_guardada

5. ESTRUCTURA INTERNA DEL campo codigo_pytest:
   a) Imports: unittest.mock, pytest, y el import del módulo real del proyecto
   b) # Arrange: mocks de dependencias externas + datos de entrada
   c) # Act: llamada al método bajo prueba (o with pytest.raises para errores)
   d) # Assert: verificaciones del resultado y llamadas a mocks

- Es un string donde los saltos de línea se representan como \n

- La lógica debe ser mínima pero real — suficiente para que la prueba pase
- Los saltos de línea se representan como \n
