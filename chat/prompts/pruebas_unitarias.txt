=== FILOSOFÍA TDD — LEE ESTO ANTES DE GENERAR ===

Estas pruebas se escriben ANTES de que exista el código real del proyecto. Siguen la metodología TDD:
1. Primero se escribe la prueba que define el CONTRATO (qué debe hacer el código)
2. Luego el desarrollador escribe el código real que haga pasar esa prueba

Por eso cada prueba debe ser completamente autosuficiente: define inline la clase o función
bajo prueba con la lógica mínima esperada. El desarrollador leerá esta prueba y sabrá
exactamente qué debe implementar en su proyecto real.

=== REGLAS PARA GENERAR PRUEBAS ===

1. COBERTURA OBLIGATORIA POR FUNCIONALIDAD:
   • Caso exitoso con datos válidos
   • Validación de campos obligatorios
   • Validación de tipos de datos incorrectos
   • Validación de formatos inválidos
   • Reglas de negocio
   • Valores límite
   • Condiciones previas no cumplidas
   • Estados inconsistentes

2. CÓDIGO PYTEST AUTOSUFICIENTE — REGLA MÁS IMPORTANTE:

   Cada prueba NO importa módulos del proyecto real. En su lugar:
   - Define la clase o función bajo prueba DENTRO del test con su lógica mínima real
   - Esa definición inline es el CONTRATO que el desarrollador debe implementar
   - Mockea SOLO dependencias externas (repositorios, servicios de terceros, BD)
   - Incluye TODOS los imports necesarios dentro de la función de test

   ✅ CORRECTO — clase definida inline con lógica real mínima:
   "codigo_pytest": "def test_crear_usuario_email_duplicado_lanza_error():\n    from unittest.mock import Mock\n    import pytest\n\n    class ServicioUsuarios:\n        def __init__(self, repo):\n            self.repo = repo\n        def crear_usuario(self, datos):\n            if self.repo.existe_email(datos['email']):\n                raise ValueError('El email ya esta registrado.')\n            return self.repo.guardar(datos)\n\n    # Arrange\n    repo_mock = Mock()\n    repo_mock.existe_email.return_value = True\n    servicio = ServicioUsuarios(repo_mock)\n\n    # Act & Assert\n    with pytest.raises(ValueError) as excinfo:\n        servicio.crear_usuario({'email': 'juan@test.com', 'nombre': 'Juan'})\n    assert 'email ya esta registrado' in str(excinfo.value)\n    repo_mock.guardar.assert_not_called()"

   ❌ INCORRECTO — importa del proyecto real:
   "codigo_pytest": "from miapp.servicios import ServicioUsuarios\ndef test_crear_usuario(): ..."

   ❌ INCORRECTO — sin lógica real, mock que siempre pasa vacío:
   "codigo_pytest": "def test_crear_usuario():\n    mock = Mock()\n    mock.crear.return_value = True\n    assert mock.crear() == True"

3. ESTRUCTURA INTERNA DEL campo "codigo_pytest":

   La función debe seguir siempre este orden:
   a) Imports dentro de la función (from unittest.mock import Mock, import pytest, etc.)
   b) Definición inline de la clase/función bajo prueba con su lógica real mínima
   c) Comentario # Arrange con configuración de mocks y datos de entrada
   d) Comentario # Act con la llamada al método (o with pytest.raises para errores)
   e) Comentario # Assert con verificaciones del resultado y llamadas a mocks

4. NOMENCLATURA:
   Formato: test_[accion]_[condicion]_[resultado]
   Ejemplos:
   • test_crear_usuario_con_email_valido_retorna_usuario_guardado
   • test_crear_usuario_con_email_duplicado_lanza_valor_error
   • test_actualizar_usuario_inexistente_retorna_none

5. DATOS DE PRUEBA:
   Usa diccionarios Python literales válidos.
   ✅ CORRECTO: "entrada": "{'nombre': 'Juan', 'edad': 25, 'activo': True}"
   ❌ INCORRECTO: "entrada": "Datos válidos de usuario"

6. PASOS (para documentación y visualización):
   Los pasos describen el flujo lógico en lenguaje natural resumido.
   El código ejecutable completo va en "codigo_pytest", no en los pasos.

=== REGLAS CRÍTICAS PARA EL CAMPO codigo_pytest ===

- Es un string donde los saltos de línea se representan como \n
- NUNCA uses comillas dobles dentro del código Python — usa SOLO comillas simples
- La función SIEMPRE empieza con "def test_"
- Todos los imports van DENTRO de la función, no fuera
- La clase bajo prueba se define DENTRO del test con su lógica real mínima
- El código debe poder ejecutarse con "pytest" sin ninguna dependencia externa del proyecto
- La lógica de la clase inline debe ser real y correcta, no un stub vacío que siempre pase

=== CONSIDERACIONES TÉCNICAS ===

• Incluye mensajes en los asserts: assert x == y, 'Descripción del fallo'
• Para pruebas con múltiples entradas similares, usa pytest.mark.parametrize dentro de codigo_pytest
• Cada prueba debe ser 100% independiente
• Para verificar excepciones usa with pytest.raises(TipoError) as excinfo seguido de assert en el mensaje

=== CALIDAD ===

• Nombres auto-explicativos que describan exactamente qué, cómo y con qué resultado se prueba
• La clase definida inline representa fielmente el contrato que el desarrollador debe implementar
• No uses stubs que siempre retornan True — la lógica inline debe validar y comportarse correctamente
• Pruebas aisladas e independientes entre sí
